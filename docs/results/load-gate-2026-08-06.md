## What the gate checks, and what it deliberately does not

The first half of the wording is a measurement. The second is partly a
documentation obligation, and a `make` target that asserted the presence
of a markdown file would be checking that somebody wrote a file, not
that a number is honest. The split is stated rather than blurred:

**Checked here** — `unaccounted` returns to zero after load drains;
`stream_skipped` stays zero; records the collector could not write are
counted; the decision p99 under load is inside the 80ms budget; the
driver kept its own schedule.

**Not checked here** — that a curve exists for each published latency.
[4.2](load-curve-2026-08-05.md) and
[4.5](decision-under-load-2026-08-05.md) produced them.

The budget is the published claim. The 1.393ms idle figure never was
one — the schema calls it a floor — and a gate requiring a floor to be
reproduced under load would fail for the wrong reason and be deleted
for it.

## Why this is not `make loss-audit` again

`loss-audit` reconciles under an induced **outage**: the archive taken
away, the broker taken away. This reconciles under sustained **load**,
where nothing is down, everything answers, and the archive simply cannot
keep up.

That distinction is not academic. It is what found the defect below.

## Proven red, twice, and the second one was not a drill

A gate nobody has seen fail is not a gate.

**The broker taken away mid-run** — after the precondition check, so the
gate is running rather than refusing:

```
FAIL  the archive did not drain after sustained ingest (unaccounted=-70.0)
FAIL  nothing was dropped under load (10222)
FAIL  every sequence the archive walked is committed or refused
FAIL  the archive did not drain after sustained decisions
FAIL  the accounting still balances after the decision load
```

Five assertions, including the one that matters most: 10 222 records
were dropped and **counted**. Loss is permitted; silence is not.

But look at the figure in parentheses. **`unaccounted = -70`.**

### A loss figure that can be negative is not a loss figure

[ADR-0008](../../contract/decisions/0008-what-a-zero-is-allowed-to-mean.md)
had `committed` counting commit *operations*, so a redelivered sequence
contributed once to `span` and twice to `committed`. Correct about rows;
wrong about sequences, and the two were conflated.

The defect shipped in PR-3.6, survived a full phase, an ADR and
`make loss-audit` — which induces outages but had never induced enough
**redelivery under load** to drive the figure past zero. It was found
within an hour of this gate existing, by the gate failing for a reason
nobody had predicted.

[ADR-0010](../../contract/decisions/0010-unaccounted-must-never-be-negative.md)
corrects it: `committed` counts distinct records, detected from
`INSERT OR IGNORE` reporting zero rows affected, and redeliveries are
counted separately as `duplicates`.

**The first fix was also wrong**, in the other direction. Subtracting
`duplicates` as well over-corrects — a redelivery adds no sequence to
the span, because the sequence was already explained by the original
commit. Twenty redeliveries of one record produced `-19` in a test
written for that first fix. The test was written before the fix was
trusted, which is the only reason the wrong correction did not ship.

### The same disruption, after the correction

```
position_committed   63286
position_rows        63286
position_duplicates      3
position_unaccounted     0
```

`unaccounted` holds at zero under the exact condition that produced −70.
The duplicates are visible and separate. The gate still fails — 9 973
records were dropped with the broker down — which is the right reason.

## A second defect, found by the first red run

Before the broker test, the gate failed on:

```
FAIL  commit operations (169104) cover the rows held (169106)
```

Two rows more than commits. Not an inconsistency in the data — a
**skewed snapshot**. The archive read `Position` and then `Count` as two
separate queries, and under load records committed in between.

Fixed with `PositionAndCount`, one read transaction, so the published
pair describes one instant. A scraper assumes that; it was not true.

## What this does not say

- **One machine, 20 seconds per phase, 2 000 sessions/s and 4 000
  decisions/s** — comfortably below the bends found in 4.2 and 4.5. This
  gate asserts the accounting holds at a sustainable rate. It is not a
  capacity test and does not replace the curves.
- **Docker Desktop on macOS is a VM.** As everywhere in this phase, the
  ratios travel and the magnitudes do not.
- **The archive is still the constraint** at ~4 133 records/s against a
  collector that bends near 16 000, and **there is still no
  backpressure**. The gate passes because the offered rate is below the
  archive's, not because the mismatch was solved.

## Reproducing

```sh
make docker-build && make up
make load-gate
```

It refuses when the topology is down.
