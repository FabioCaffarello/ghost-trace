> RFCs in Ghost Trace are proposals subject to constitutional review. The [Constitutional Charter](../charter/constitutional-charter.md) is the authoritative reference. RFCs that conflict with the Charter must either be rejected or accompanied by a corresponding charter amendment (see [`../charter/amendments.md`](../charter/amendments.md)).

## Summary

One paragraph. What does this RFC propose? Why?

## Motivation

Why is this change necessary? What problem does it solve? What is the cost of *not* making the change?

## Constitutional Review

Required for every RFC. Identify:

- Which Charter invariants the proposal interacts with.
- Whether the proposal satisfies each interacting invariant, and how.
- Whether the proposal requires amendment of any Charter element. If yes, the proposal is classified as `charter-amendment` and must follow the amendment process.

Proposals that introduce non-falsifiable language at the Charter level are rejected on procedural grounds.

## Proposal

The substance of the RFC. Be concrete. Include:

- Structural changes (schema, contracts, types).
- Behavioral changes (operations, lifecycles, semantics).
- Operational changes (deployment, observability, runbook impact).
- Document changes (Ontology, architecture, schemas).

## Alternatives Considered

What other approaches were considered? Why were they not chosen?

## Open Questions

What remains undecided? What does this RFC explicitly defer?

## Anti-Patterns to Avoid

What failure modes would emerge if this proposal were implemented carelessly?

## Migration and Backward Compatibility

If this proposal changes existing behavior, how is migration handled? How is the old behavior preserved for replay of historical data?
